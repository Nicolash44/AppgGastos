## Design Specificity Verdict

**LLM assessment**: This could ship unchanged in any expense tracker, todo app, or e-commerce filter bar — zero product-specific texture. Both new controls use `bg-slate-900 text-white` for their active state regardless of which option is selected, so color carries no semantic information. Contrast this with DESIGN.md's own ingreso/gasto chip pattern, where "the chip itself becomes a preview of the movement type" via solid emerald/rose fill — specific, considered, tied to meaning. Here it's a generic dark-pill toggle bolted onto a page that otherwise has a deliberate color language. This is the mechanical root of the user's own complaint: "parece un trabajo sin contexto alguno."

## Overall Impression

The engineering is careful — RLS-safe defaults, non-breaking migration, correct focus rings, correct hardcoded accessibility border color reused from the rest of the app — but the interface layer was shipped as if it were an internal admin toggle, not a user-facing concept with real bookkeeping consequences for the exact audience (monotributistas) the business is trying to sell to. The single biggest opportunity: this app already solved "how do we explain a feature in one sentence without slowing anyone down" with the (i)-icon popover pattern next to Categorías and Comparar meses — and this feature is the one that needed it most, yet is the one place it wasn't used.

## What's Working

- Accessibility mechanics are correct and consistent with the rest of the app: `focus-visible:ring-2 focus-visible:ring-offset-1 focus-visible:ring-slate-400` and the custom `border-[#8594aa]` neutral border both match the project's already-established, deliberately-fixed accessibility baseline — whoever wrote this read the existing file's conventions rather than inventing new ones.
- Correct restraint on color: not inventing a third accent hue for this feature follows DESIGN.md's explicit rule ("don't add a third accent color for a new feature"). The execution failed to communicate meaning, but the constraint itself was respected.
- The account toggle is gated behind `x-show="categoria"`, avoiding showing an extra control before the user has committed to logging something — some awareness of not front-loading the form, even though the net effect still adds a decision before the amount field.

## Priority Issues

**[P0] What**: No copy or help mechanism explains what "Laburo" vs "Personal" means, anywhere in the feature.
**Why it matters**: This is the direct, literal cause of the user's own complaint. For a monotributista, a wrongly-understood category can misstate income for tax bookkeeping — a real financial consequence, not a cosmetic one. The app already has a proven, reusable pattern for exactly this (the (i)-icon dark popover next to "Categorías"/"Comparar meses") that wasn't applied here.
**Fix**: Add the existing (i)-icon + popover pattern next to the filter tabs and/or above the account toggle, with 1-2 plain-language sentences (e.g. "Laburo: gastos e ingresos de tu facturación. Personal: todo lo demás.").
**Suggested command**: `/impeccable clarify`

**[P0] What**: The filter tabs have no visible label and sit directly above the sticky balance number, silently changing what that number means with no other on-page indication once selected.
**Why it matters**: A user could set the filter to "Laburo," come back later, see a much lower balance than expected, and think money is missing — a trust-destroying false alarm in a finance app.
**Fix**: Add a persistent indicator near the balance when a non-"Todos" filter is active (e.g. "Mostrando: Laburo" next to the total), and/or reset the filter to "Todos" each session instead of persisting it silently.
**Suggested command**: `/impeccable harden`

**[P1] What**: The account toggle's active-state color (`bg-slate-900` for both "Personal" and "Laburo") carries no semantic distinction, unlike the emerald/rose ingreso/gasto chip pattern this app already uses for a conceptually similar binary choice — confirmed by the detector as a plain reuse of existing slate tokens, no novel drift, just no meaning attached.
**Why it matters**: Two visually identical "modes" for a decision with real tax consequences increases misclick risk and gives the whole feature a bolted-on feel.
**Fix**: Give "Laburo" and "Personal" distinct but understated real identities within the existing palette (e.g. navy fill vs. slate fill) rather than one shared dark pill for both.
**Suggested command**: `/impeccable colorize`

**[P1] What**: The list-view "Laburo" tag only ever appears for laburo items, never for personal ones (even in "Todos" view), making personal transactions look like the unlabeled default and laburo ones look flagged/exceptional.
**Why it matters**: Visually implies "Laburo" is an edge case rather than an equal half of the new mental model, undermining the feature's own premise.
**Fix**: Show both tags symmetrically in "Todos" view, or show neither and rely purely on the filter — pick one consistent rule.
**Suggested command**: `/impeccable polish`

**[P2] What**: Both new controls lack `aria-pressed`/`role="radiogroup"` semantics (confirmed by manual/detector-adjacent review) and use non-standard sizing (`h-7` tabs, `h-10` toggle vs. this form's existing `h-11`/`h-12`/`h-14` scale, and a `text-[10px]` arbitrary value flagged directly by the detector as off the DESIGN.md type ramp).
**Why it matters**: Compounds the "not-designed-for-this-app" feeling with concrete accessibility and consistency debt, and the 10px pill is likely under WCAG contrast at that size per the detector's independently-flagged `#64748b`-on-light-slate pairing.
**Fix**: Add `aria-pressed`/`role="radiogroup"` to both toggle groups, snap the account toggle to `h-11` to match the form's own inputs, and replace `text-[10px]` with `text-xs` (12px, the smallest existing step in this file) with a higher-contrast text color.
**Suggested command**: `/impeccable audit`

**[P2] What**: Nothing in the markup gates the filter tabs or account toggle behind a "this user is a monotributista" flag — they render globally for every account, including the plain household-budgeting persona this app also serves.
**Why it matters**: For a non-freelancer user, this is unexplained clutter injected into the fastest, most protected part of the app, in direct tension with the product's own "fricción mínima... sin configuración obligatoria" principle.
**Fix**: Gate visibility behind a one-time onboarding question ("¿Sos monotributista?") or profile flag, defaulting hidden for users who don't opt in.
**Suggested command**: `/impeccable onboard`

## Persona Red Flags

**Jordan (confused first-timer, general household user — not self-employed)**
- Sees three unlabeled tabs ("Todos / Personal / Laburo") appear above the balance with zero explanation, and doesn't know if this even applies to them.
- Sees a pair of buttons ("Personal"/"Laburo") appear in the transaction form right before the amount field and doesn't know what to pick, when the product's whole promise to them was "categoría + monto en segundos."
- Might tap one by accident (silent localStorage default, possibly empty on first load) and never notice, since there's no visible confirmation in most views.

**Mica (project-specific persona: monotributista freelancer, low patience for ambiguity in money categorization since misclassifying affects her tax bookkeeping)**
- Immediately needs to know: does "Laburo" mean gross billing income only, or does it include work-related expenses too? The single word doesn't disambiguate scope, and there's no help text — exactly the kind of ambiguity she has zero patience for.
- Transactions logged before this feature shipped presumably have no `cuenta` value; if she filters to "Laburo" expecting her billing history, older entries may silently disappear from that view with no "these predate this feature" message, making her think data was lost.
- The silent localStorage-persisted default means if she forgets to switch the toggle back after a personal expense, subsequent entries could get silently mis-tagged with no periodic "review your laburo total" sanity check — directly threatening the exact failure she fears.

## Minor Observations

- Filter tabs are `h-7` (28px) — smaller than every other interactive control in this form/dashboard area, and smaller than the account toggle buttons (`h-10`) for what is arguably a more consequential, page-wide-scope decision.
- `active:scale-[0.97]` micro-interaction is present on the account toggle but not on the filter tabs — an inconsistency in tactile feedback between two conceptually identical controls shipped together.
- No loading/transition acknowledgment when switching `cuentaFiltro` beyond the tab's own selected state — `renderChartCategorias()` re-renders the chart with no visual confirmation.
- Detector flagged a stray 14px font-size elsewhere in the file (index.html:42) unrelated to this feature — pre-existing, noted for completeness only.

## Questions to Consider

1. If a regular non-freelancer user never needs "Personal vs. Laburo," why is this shipped as global always-on UI instead of opt-in — doesn't its universal presence quietly contradict the product's own "sin configuración obligatoria" principle?
2. This app already solved "explain a feature in one sentence without slowing anyone down" with the (i)-icon pattern two components away in the same file — what would it take to make reaching for existing patterns the default reflex before shipping new UI?
3. Is the real mental model here "two symmetric accounts" or secretly "flag the exception" (since only "Laburo" ever gets a visible tag)? If it's the latter, should this be reframed as a single "Es de laburo" flag rather than a binary toggle?
